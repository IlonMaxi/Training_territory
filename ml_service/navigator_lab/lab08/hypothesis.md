# Вывод и гипотеза для ЛР 9

## Вывод

Baseline не проходит ни один порог альфа-версии: macro-F1 0.425 при пороге 0.70, accuracy 0.460 при 0.75, ошибочных переходов 23 из 63 при допустимых 10%. Три раздела (clients, support, trainer) не находятся ни разу.

Главный источник ошибок - словарь. В 28 из 34 ошибок в запросе есть слово, которого нет в train: в 10 случаях это другая форма известного слова, в 18 - новое слово. Ошибок при полностью известных словах всего 6. Опечатки дают тот же эффект: одна перестановка букв ломает 9 из 29 верных ответов, а R1 прямо требует учитывать опечатки.

Самая вредная ошибка - ошибочный переход, и в 12 из 21 таких случаев по запросам к разделам нужный раздел был бы среди трёх кнопок. Часть ошибок связана не с моделью, а со спорной границей в инструкции разметки: 7 из 11 запросов со сложной разметкой.

## Почему следующая гипотеза про формы слов

- **Формы слов и опечатки** - одна проверяемая причина: сравниваются целые слова. Её можно исправить изменением признаков, не трогая данные и split.
- **Новые слова** (18 ошибок) на зафиксированных данных не исправить: если дописать фразы в train после просмотра validation, это будет утечка. Для них нужны реальные запросы из журнала событий.
- **Стоп-слова** (H2) и **порог уверенности с кнопками** (H3) - отдельные изменения. Если проверять их вместе с H1, будет непонятно, что именно дало эффект. Поэтому они идут следующими, по одной.

## Карточка гипотезы H1

| Поле | Значение |
|---|---|
| Гипотеза | Если сравнивать запросы по символьным n-граммам длиной 3-5 внутри слов вместо целых слов, baseline начнёт связывать формы одного слова и слова с опечатками, и macro-F1 на validation вырастет минимум на 0.10 |
| Из какого наблюдения | 10 из 34 ошибок: слово есть в train в другой форме; 9 из 29 верных ответов ломаются от одной перестановки букв |
| Что меняется | Только признаки: TF-IDF по n-граммам 3-5 символов внутри слов (как `analyzer='char_wb', ngram_range=(3, 5)` в scikit-learn) вместо целых слов. Так же признаки устроены в плане проекта |
| Что зафиксировано | Данные clean v2 (60d80a7acb7eb7fa), split, IDF только по train, ответ по ближайшему запросу train, порядок равных оценок, пустой ответ считается ошибкой, `metrics.py`, 63 запроса validation. Test не используется |
| Ожидаемый эффект | macro-F1 не ниже 0.525 (0.425 + 0.10); из 10 ошибок с формой слова исправится не меньше 5; в спецтесте опечаток верных останется больше 20 из 29 |
| Защитные условия | Доля ошибочных переходов не выше 0.365, как у baseline; намерений с нулевым recall не больше 3; посторонних запросов, открывших раздел, не больше 2 из 8 |
| Отрицательный результат | Прирост macro-F1 меньше 0.10 или ухудшилось любое защитное условие - гипотеза не подтверждена. Если macro-F1 вырос, а ошибки с формой слова не исправились, рост дала другая причина, и механизм гипотезы тоже не подтверждён |
| Почему порог 0.10 | Интервал macro-F1 baseline 0.319-0.504: на 63 запросах изменения меньше 0.10 нельзя отличить от случайных |
| Риск | У служебных слов («мои», «на») тоже есть общие n-граммы, они могут дать новые ошибочные переходы. Это поймает защитное условие, а удаление стоп-слов будет следующей гипотезой H2 |
| Что гипотеза не проверяет | Новые слова (нужны реальные запросы), порог уверенности и кнопки (H3), поведение настоящих пользователей (журнал событий из задания 2) |

## Самопроверка

**Какая ошибка наиболее вредна пользователю и как её заметить?** Самая вредная из частых - ошибочный переход: навигатор пишет «Открываю: ...» и открывает не тот раздел. Пользователю нужно вернуться и искать заново, и он перестаёт доверять навигатору. Её видно по доле ошибочных переходов (23 из 63) и по матрице ошибок, которая показывает конкретные пары: clients → schedule, nutrition → schedule, progress → clients, support → workout. Один macro-F1 смешал бы её с отказами.

Самая вредная из редких - переход в раздел другой роли. Её не видно ни в одной офлайн-метрике, поэтому её держит фильтр интерфейса до перехода, и проверяется она по коду.
