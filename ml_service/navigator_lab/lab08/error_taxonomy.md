# Baseline по сегментам и таксономия ошибок

Все числа рассчитаны командой `python -m navigator_lab analyze` по 63 запросам validation, файлы лежат в `results/lab08`. Модель та же, что в ЛР 7.

## Сегменты

Сегменты заданы до просмотра ответов модели: по словарю train, по длине запроса, по разметке ЛР 6 и по теме. Сложная разметка - это запросы, где разметчик B поставил уверенность 2 или не согласился с итоговой меткой.

| Разрез | Сегмент | Запросов | Верно | Accuracy | Нет ответа | Ошибочных переходов |
|---|---|---|---|---|---|---|
| Словарь train | все слова известны | 15 | 9 | 0.600 | 0 | 5 |
| | часть слов неизвестна | 40 | 20 | 0.500 | 0 | 18 |
| | нет известных слов | 8 | 0 | 0 | 8 | 0 |
| Длина | 1 слово | 4 | 1 | 0.250 | 3 | 0 |
| | 2 слова | 34 | 13 | 0.382 | 4 | 16 |
| | 3 слова и больше | 25 | 15 | 0.600 | 1 | 7 |
| Разметка ЛР 6 | уверенная | 52 | 25 | 0.481 | 8 | 17 |
| | сложная | 11 | 4 | 0.364 | 0 | 6 |
| Тема | разделы платформы | 55 | 25 | 0.455 | 6 | 21 |
| | посторонние (other) | 8 | 4 | 0.500 | 2 | 2 |

Что видно:

- Даже когда все слова запроса есть в train, верно только 9 из 15. Значит, дело не только в словаре: решение по одному ближайшему запросу тоже ошибается.
- Короткие запросы хуже длинных: из одного слова верно 1 из 4, из двух - 13 из 34, из трёх и больше - 15 из 25. В запросах из двух слов часто одно слово служебное («мои», «моё»), а второго нет в train, и ответ выбирается по служебному слову.
- Сегменты маленькие: в «1 слово» 4 запроса, в сложной разметке 11. Разница 0.364 против 0.481 - это 7 ошибок из 11 против 27 из 52, по ней нельзя делать сильных выводов.

## Таксономия ошибок

Первые три типа делят 34 ошибки по словарю и не пересекаются: 10 + 18 + 6 = 34. Остальные типы проходят поперёк этого деления, поэтому у каждого свой знаменатель. ID всех запросов каждого типа есть в `results/lab08/error_taxonomy.csv`, тип каждого запроса - в `validation_cases.csv`.

**Основная выборка (validation)**

| Тип | Частота | Пример и проверенная причина | Ущерб | Следующий шаг |
|---|---|---|---|---|
| Слово в другой форме | 10 из 34 ошибок: 7 неверных ответов, 3 без ответа | «абонемент» - нет ответа, в train только «абонемента»; «какие есть тренеры» → subscription, в train «тренера». Причина: сравниваются целые слова. Проверка: у неизвестного слова есть слово train с теми же первыми 5 буквами, все 10 пар просмотрены вручную | Средний: не тот раздел или нет ответа | Гипотеза H1 для ЛР 9: символьные n-граммы |
| Новое слово | 18 из 34 ошибок: 13 неверных ответов, 5 без ответа | «моё питание» → schedule: слова «питание» нет в train ни в какой форме, ответ выбран по «моё». Так же «аватар», «пожаловаться», «диалог» | Средний | Пополнять train реальными запросами из журнала событий (задание 2). На зафиксированных данных это не исправить: добавлять фразы после просмотра validation - утечка |
| Все слова известны | 6 из 34 ошибок | «мои замеры» → clients: «замеры» есть и в progress, и в clients, ближе оказался короткий «замеры клиента». «написать комментарий» → chat, хотя второй и третий соседи - feedback | Средний | Решение по нескольким соседям: по меткам трёх ближайших исправились бы 2 из 6. Отдельная гипотеза после H1 |
| Нет ответа | 8 из 63 запросов | «пожаловаться», «куда нажать», «абонемент» | Низкий: видно, что навигатор не понял, есть меню | Допустимо в alpha; H1 должна уменьшить, так как 3 из 8 - формы слов |
| Ответ только по стоп-словам | 7 из 26 неверных ответов; ещё 2 из 29 верных держатся только на стоп-словах | «мои калории» → schedule по «мои»; «расскажи о себе» → trainer по «о». Проверка: общие слова с ближайшим запросом все из списка стоп-слов сервиса, тест сверяет список с `main.py` | Средний | Гипотеза H2: удалять стоп-слова сервиса. Проверять после H1, не вместе с ней |
| Сложная разметка | 7 из 11 запросов со сложной разметкой ошибочны, в уверенной 27 из 52 | «показать замеры» → clients, разметчик B писал «мог быть clients»; «добавить занятие клиенту» → schedule, B писал «может быть schedule»; «рецепт пиццы» → nutrition, как и метка B | Не только ошибка модели: граница в инструкции спорная | Проверить инструкцию на тренере клуба, а не подгонять модель под эти запросы |
| Посторонний запрос открыл раздел | 2 из 8 посторонних запросов | «расскажи о себе» → trainer, «рецепт пиццы» → nutrition | Средний (R2) | Порог уверенности и кнопки (R3), отдельная гипотеза |

|---|---|---|---|---|

Если запрос задал клиент, `available()` не даст открыть раздел и покажет кнопки | Недопустимо, если откроется (R4) | Фильтр перед переходом оставить, добавить автотест интерфейса: сейчас проверка только по коду |

## Связь с требованиями

| Ошибка | В альфа-версии | Требование | Владелец риска |
|---|---|---|---|
| Переход в раздел другой роли | Недопустима, должно быть 0 | R4 | Руководитель проекта; фильтр делает Frontend-агент, проверяет QA-агент |
| Ошибочный переход | Допустим не чаще 10% запросов | R1, R3 | Разработчик моделей |
| Посторонний запрос открыл раздел | Не больше 1 из 8 | R2 | Разработчик моделей |
| Нет ответа, уточнение кнопками | Допустимо: пользователь видит, что навигатор не понял, и выбирает раздел сам | R3 | Руководитель проекта |
| Опечатки и формы слов | Допустимы только как известное ограничение baseline | R1 | Разработчик моделей |
| Латиница | Допустима, если в интерфейсе сказано про русский язык | - | Разработчик интерфейса (Frontend-агент) |
| Неверный ввод | Только явная ошибка, без падения | - | ML-инженер (ML-агент), проверка QA-агент |

Роли взяты из задания 2. Решения о данных, моделях и порогах остаются за исполнителем проекта, агенты только реализуют и проверяют.

Отдельно о кнопках (R3). В 39 из 55 запросов к разделам платформы нужный раздел был бы среди трёх кнопок, хотя первым ответом он верен только в 25. Из 21 ошибочного перехода по таким запросам в 12 нужная кнопка была бы на экране. Значит, порог уверенности с кнопками превратил бы часть дорогих ошибок в дешёвые уточнения. Это отдельная проверка после H1: она снижает вред, но не устраняет причину ошибок.
